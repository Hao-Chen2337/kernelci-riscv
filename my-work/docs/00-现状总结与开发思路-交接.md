## 3. 引擎选型的完整讨论结论

见 §0.3–0.4。补充判断依据:
- 上游真实使用量实测:`grep 'type: lava|pull_labs|...' config/scheduler*.yaml` → lava 35 / pull_labs 12 / shell 1 / docker 1(注释)。
- "自托管 LAVA"与"pull_labs+tuxrun"的差距不在"写配置",而在 **lab 侧职责**:LAVA 模式 lab 侧零代码(服务器管执行+回传),pull_labs 模式 lab 侧要有执行器(官方 example_pull_lab.py 是玩具;tuxrun 是官方钦定执行器,requirements.txt 里写明依赖 tuxrun)。
- **为什么 LAVA 难"一键"**:不是安装难(danrue/lava-docker-compose 可半天拉起),而是(1) dispatcher root/设备权限;(2) **回调方向**:LAVA 服务器要把结果推回本地 lava_callback,网络可达常被忽略;(3) 有状态服务(Django/Postgres/RabbitMQ)要长期运维升级。纯 QEMU 虚拟设备场景这三点全部弱化,LAVA 自托管值得认真考虑。
- **kernelci 开源意义/两种用法**:当用户(往 kernelci.org 加档案、让社区 lab 跑)或当自建(自己 docker compose 拉一套)。SOW 的 localized 指向"自己能跑的闭环",交付仍是配置+PR。
- k8s 引擎不建议:跑测试要自带含 qemu 的执行镜像+自己养集群,运维比 LAVA 更重,等于回到"发布执行镜像"的老问题。

## 6. tuxrun 路线的细节清单(本会话已核实/待核实)

已核实:
- cpu 覆盖经 `--parameters cpu=rv64,v=true,h=true`(进 device dict)。
- kselftest-kvm 类在 qemu-riscv64 上可用(继承 qemu-* 设备),渲染含 modules/kselftest overlay。
- kselftest-riscv 需 4 行 tuxlava 登记类(补丁已实测)。
- baseline 只能 ext4 盘登录(qemu device 不认 cpio ramdisk;内核 boot 回归信号不变;可用 --rootfs 覆盖)。
- TAP 顶层行形如 `ok N selftests: riscv: X`/`not ok N ...`;tuxrun 日志每行带 ANSI 色码+时间戳前缀,解析需先剥色码、允许前缀(tap_summary 已实现并用真日志验证)。
- LKFT 执行器(`Linaro/test-definitions` automated/linux/kselftest/)支持 TST_CMDFILES + TST_CASENAME + SKIPFILE/SKIPLIST + SHARD;`kselftest.sh -T` 把 allow-list 交给 `run_kselftest.sh -t` 精确匹配 `kvm:test名`。**KVM 9 项精选已按 TST_CASENAME allow-list 接线**(tuxlava 模板转发补丁 + worker 默认 `KVM_TEST_SUBSET`),比 SKIPFILE 近似更干净——SKIPFILE/SKIPLIST 是"跳名单"(要枚举全集其余项),TST_CASENAME 是"白名单"。
