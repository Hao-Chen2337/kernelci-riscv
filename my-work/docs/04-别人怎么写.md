# 04 别人怎么写：KernelCI pull-lab 的代码量级与正确姿势（参照系）

## TL;DR

1. 上游官方对"接入一个 pull lab"的期待 = **装 tuxrun/podman、跑 `tools/example_pull_lab.py`**（`doc/connecting-pull-lab.md`），即 lab 侧执行层预期接近 0 行自研；官方脚本是"协议层示例"，不是生产实现（poll 语义过时、按 Enter 才跑、不执行 job 的 tests[]）。
2. 三个 example 的执行层全部外包：tuxrun 子进程（361 行里执行仅 ~57 行）/ pytest+labgrid（conftest 122 行）/ 本地 LAVA（459 行只做"提交"，结果由 LAVA callback 回传）。
3. "和 guest 说话"在成熟项目里是**分层库**而非应用代码：tuxrun(2,003 行) → tuxlava(5,929 行) 生成 LAVA job → lava-dispatcher(28,956 行, pexpect 驱动串口) → guest 侧 lava-test-shell 打 `LAVA_SIGNAL` 标记；用户 worker 的 ===DONE=== 思路与 LAVA_SIGNAL 同构。
4. 对等仓库 xjysiiau/kernelci-riscv、Acidmoon/kernelci-riscv-li3a 都不是 pull-lab worker、不打算 PR 上游（SSH 驱动真机/QEMU），不能当"779 行是否超编"的直接参照。
5. 779 行里真正"重复造轮子"的是 ~250 行 PTY/rootfs 执行层（tuxrun/LAVA 已解决）；协议层 state=available 语义、幂等/状态持久化/安全解包是上游 example 反而没有的、生产 lab 必需的部分。

---

## 1. 官方文档：lab 侧被期待成什么样

`kernelci-pipeline/doc/connecting-pull-lab.md`（本地 clone 与上游 main 逐字节相同，raw 抓取 diff 为 SAME）：

- L8-13：pull-lab 是官方一等公民 runtime，协议出处是 kernelci/kernelci-core PR #3008（"runtime: Add Pull-Only labs runtime implementation"，nuclearcat，2025-11 评论）；"There is an payload script in `tools/example_pull_lab.py`..."——**官方给 lab 的交付物就是一个 example 脚本**。
- L97-124（Running the Example Pull Lab Script）：前提 = `pip install -r tools/requirements.txt` + podman 或 docker + tuxrun，"Tuxrun handles downloads and QEMU VM execution automatically"。L123-124 明写 **TODO：FVP/DUT 支持"future"**——脚本性质是演示。
- L126-161：pytest+labgrid 是替代路线；L163-215：LAVA 拉取式 lab 用 `example_pull_lab_lava.py`（"submits the definitions verbatim to its local LAVA instance"，结果由定义内 notify callback 回传）。
- 上游不提供也不维护任何"lab 生产 daemon"：`tools/` 全目录 = 3 个 example_api_*、3 个 example_pull_lab_*、example_pytest_tests/、3 个小运维脚本（extract_compatible.py 126 行、jwt_generator.py 111 行、sync_stable_branches.py 200 行）+ tools/cron/kci-dev.toml（13 行）。**无一个常驻 worker 先例**。

注意：example 的 poll 是 `?state=done&kind=job`（example_pull_lab.py:29），而当前 scheduler 对 pull_labs 把 job node 置 `available`（`src/scheduler.py:918-921` 注释："pull_labs workers poll for jobs in 'available' state"，本地与上游 main 同文件 SAME）。用户 worker 用 state=available 是对的，example 是旧的。

## 2. 三个 example 的职责切分（协议层 vs 执行层）

| 脚本 | 行数 | 自己写的（协议层） | 外包的（执行层） | 关键证据行 |
|---|---|---|---|---|
| example_pull_lab.py | 361 | poll 事件 / 下载 job 定义 / 过滤 platform-runtime-group / 拼 `tuxrun` argv / cache-dir 落盘 | `subprocess.run(["tuxrun", ...])`，tuxrun 自己下载 kernel/modules/rootfs 并驱动 QEMU | run_tuxrun 仅在 L57-113（~57 行），L80-88 拼 argv，L106 subprocess |
| example_pull_lab_pytest.py | 261 | 同上 poll/过滤骨架；把 job json 写临时文件 | `subprocess.run([python, -m, pytest])`；真正起 QEMU+登录在 `tools/example_pytest_tests/conftest.py`（122 行：下载 kernel/ramdisk → 生成 labgrid env.yaml → `ShellDriver` 管 login/prompt） | conftest.py L45-68 QEMUDriver+ShellDriver 配置，L59 "login:" prompt、root 用户 |
| example_pull_lab_lava.py | 459 | poll + **JSONL journal**（~90 行，崩溃安全、compaction） + LAVA REST 提交 + 可选 wait | 整个执行交给本地 LAVA dispatcher；结果由 job 定义内 notify callback 回传，脚本零结果处理 | L21-27 docstring、L80-170 Journal、L189-203 submit |

**结论：上游眼里 lab 侧协议层 ~150-300 行，执行层 0 行自研**（tuxrun/labgrid/LAVA 替你做）。即便 pytest 路线也要自己写 guest 驱动，官方选择把这块给 labgrid 库而不是手写 PTY。

## 3. tuxrun 内部：guest 驱动在谁手里、多少行、什么手法

pypi tuxrun 1.10.0 sdist（/tmp 解包实测）：

| 层 | 规模 | 手法 |
|---|---|---|
| tuxrun CLI（pypi tuxrun 1.10.0，`tuxrun/*.py`） | 2,003 行 | 只做 CLI/argv/下载/job 生成/结果解析 |
| tuxlava 库（0.24.0，prod 5,929 行；devices/qemu.py 599、tests/kselftest.py 750、tests/ltp.py 167） | 5,929 行 | **生成 LAVA job definition**：设备=LAVA device type；tuxrun README L70 自述 "uses TuxLAVA library to generate LAVA job definition files" |
| lava-dispatcher（gitlab.com/lava/lava，shallow clone 40MB） | lava_dispatcher 28,956 行 + lava_common 3,644 行 | pexpect：shell.py:19、action.py:18 `import pexpect`；connections/serial.py:35 注释 "wraps the pexpect" |
| lava-test-shell（guest 侧工具集） | 592 行 sh | 在 guest 里执行测试并打 `<LAVA_SIGNAL_STARTTC/ENDTC/TESTCASE>` 串口标记（tuxrun/results.py:74-93 反向从日志找这些标记） |
| tuxrun 运行载体 | — | runtimes.py:156 以 `--entrypoint /usr/bin/lava-run` 起 dispatcher 容器；Dockerfile.tuxrun-dispatcher 基于 `lava-dispatcher:2026.05.dev0091`，装 qemu-system-riscv 等 |

即：**tuxrun 自述架构 = tuxlava 把"跑什么测试、用什么设备/rootfs"翻译成 LAVA job → LAVA dispatcher 用 pexpect 跟串口说话**。用户 worker 里自研的 serial_reader/登录检测/杀 QEMU/===DONE===，在 LAVA 生态里分别对应 ShellSession/pexpect、AutoLoginAction、RetryAction、lava-test-shell 标记——都是 12 年维护的库代码。

tuxrun 设备表含 `qemu-riscv32/64`（docs/devices.md:53-54，virt/rv64/Image）。但 kselftest 测试类里**没有 riscv 子类**（tuxlava/tests/kselftest.py 有 arm64/acct/alsa/…；`KSelfTest.devices=["qemu-*",...]` 全 qemu 可用而 riscv 专属 collection 无映射）——tuxrun 今天能否表达"kselftest-riscv/kvm 子集 + ssnpm"**未验证**（需真机 `tuxrun --list-tests --device qemu-riscv64`）。

## 4. kernelci-core / LAVA 的对照实现

- **pull_labs.jinja2**（kernelci-core config/runtime/base/，100 行）：只把 node artifacts(kernel/modules/kselftest/rootfs/ramdisk/initrd/dtb) + tests[](id/type/depends/timeout_s/pre-commands/…) 渲染成 job 定义 JSON——**job 定义不含任何"怎么执行"**，执行完全推给 lab。内核里另有 kernelci-core/kernelci/runtime/pull_labs.py 443 行（pipeline 侧 runtime 驱动）。
- **lava.jinja2**（88 行）+ boot/qemu.jinja2 + tests/*.jinja2：LAVA 路线里 kselftest 执行 = **整段外包给 linaro/test-definitions 的 automated/linux/kselftest/kselftest.yaml**（tests/kselftest.jinja2:19-30，参数 TESTPROG_URL=kselftest tar、TST_CMDFILES=collections、SKIP_INSTALL、ENV）——即上游自己的 collection 语义也是喂给 linaro 维护的测试定义，不在 KernelCI 仓库写执行逻辑。
- LAVA dispatcher QEMU 路径：lava_dispatcher/actions/boot/qemu.py 374 行（BootQEMUImageAction：pipeline=CallQemu→AutoLogin→ExpectShellSession→OverlayUnpack）、boot_strategy.py 795 行、shell.py 489 行（ExpectShellSession）、connections/serial.py 327 行（QemuSession 继承 ShellSession）。
- kubernetes.jinja2（83 行）= 在集群里起 pod 跑 `runtime_image` 容器 + shell command（compile/run 在 pod 内，不驱动真机 guest）——与"在目标上跑测试"是两条路。

## 5. 对等仓库（xjysiiau / Acidmoon）怎么驱动 guest

| 仓库（/tmp shallow clone） | 形态 | 驱动手法 | 与用户 worker 的差异 |
|---|---|---|---|
| xjysiiau/kernelci-riscv（~1,000 行 sh/py，docs+results+patches） | 本地闭环 CI 工作区（非 pull-lab、非上游 PR） | 预置 SSH 公钥进 rootfs 镜像（seed-test-image.sh：loop 挂载 parted 偏移分区、写 authorized_keys）→ QEMU `-snapshot` 起机 + hostfwd :22 → **SSH 进 guest 跑测试**；boot-test.sh(72 行) = 直接 `timeout qemu ... > log` 然后 **grep login:/panic** 判定 | 完全绕开 PTY 串口（用 SSH/日志 grep）；也比用户的 ext4/ctypes/mount hack 粗，且不支持"交互式登录后跑指令集子集"的协议化回收 |
| Acidmoon/kernelci-riscv-li3a（真机侧，~20 文件） | LicheePi 3A 真机验证工作区 | `ssh lpi3a 'bash ...'` + scp 同步测试文件 + grep PASS/FAIL | 真机/SSH，同属 Phase2 级本地验证，非 pull-lab 执行器 |

两者共同点：**都是给"自己看"的工作区仓库，把 guest 交互问题用 SSH 或日志 grep 消掉**，没有可给综合代理作"上游惯例"参考的 lab worker 实现；它们也印证"guest 驱动难"是普遍痛点，但解决姿势与用户（要 PR 上游的 worker）不同。

## 6. 资深视角评审（779 行对不对）

**重复造轮子的部分（tuxrun/LAVA 已解决，用户重复解决）**：
- PTY 串口会话层（serial_reader/select/threading/login 检测）≈ LAVA shell.py+serial.py 的 pexpect 封装；写进 tools/ 即把 28,956 行里最成熟的 800 行重写一遍，且难以达到其健壮性。
- rootfs ext4 烘焙 + mount /proc /sys 的 ctypes hack：LAVA/linaro rootfs 体系（rootfs.ext4.zst/overlay）与 tuxrun "handles downloads and QEMU execution automatically"（doc L109）已覆盖；tuxlava devices 定义里带 arch 专属 boot_args/rootfs。
- ===DONE=== 串口标记回收：与 lava-test-shell 的 LAVA_SIGNAL 完全同构，属已解决领域。

**确实难以外包、自研合理**：
- 上游 example 不执行 job 的 tests[]（只 print，example_pull_lab.py:283-289）——跑 baseline/kselftest/kvm 三类并逐个回传，上游示例没给答案；
- kselftest-riscv / kselftest-kvm(collection) 在 tuxlava 无现成测试类（未验证，见 §3），且 QEMU `-cpu rv64,v=true,ssnpm=true` 这类 TCG 特性参数与"9/9 全绿"的实测基线（QEMU≥9.1，用户 §8）是 lab 环境差异，tuxrun 设备 profile 不表达；
- 协议侧 state=available、幂等/状态持久化/flock、Content-Length+sha256 校验、安全解包：example 全都没有（只有 lava 版有 journal），生产 lab 必需——这 ~180 行不是浪费，是 example 与 production 的差距。

**体裁判断**：上游 tools/ 只有 example_* + ≤200 行运维脚本 + cron 配置；779 行常驻 daemon 若并入 PR2，需在 PR 里说清"官方 example 是演示、pull-lab 尚无生产 lab 执行器"；更稳妥是与上游讨论把执行层换 tuxrun（用户 §8 已列长期项），并把自研收窄到"job 定义 tests[] → 本地执行"适配层。

**行数参照**（给综合代理）：lab 协议层 150-300（example 实测）；tuxrun 全套执行栈 ≈37k 行（tuxrun 2,003 + tuxlava 5,929 + dispatcher 28,956 + test-shell 592）；peer 仓库 ~1,000 行/仓但非同一交付物。

## 留给综合代理的关键判断/数字

1. 上游官方期待 lab 执行层 ≈0 行自研（connecting-pull-lab.md L99-109：跑 example_pull_lab.py + tuxrun）；779 行 = 协议~150 + 执行~250 + 健壮性~180 + 注释，超官方预期的主要是执行层。
2. 三个 example：361(执行 57)/261(+122 conftest)/459——协议层 150-300 行、执行全外包；上游"协议层有多薄"的答案：薄到不含任何 guest 驱动。
3. "和 guest 说话"成熟形态是库：pexpect(LAVA shell.py:19/serial.py:35) + lava-test-shell LAVA_SIGNAL 标记 + labgrid ShellDriver；===DONE===/serial_reader 属已解决领域。
4. tuxrun qemu-riscv64 设备存在(devices.md:53)，但 tuxlava 无 kselftest-riscv 测试类——"tuxrun 能否直接跑 riscv kselftest 子集"**未验证**，是 PR 讨论里该实测/问上游的点。
5. upstream main 的 scheduler.py:918-921 确认 pull_labs 用 state=available（用户 worker 正确，example 的 state=done 是陈旧的）——说明 example 非生产基准，PR 时可引用此点。
6. 体裁红线：上游 tools/ 无生产 daemon 先例；779 行 worker 进 PR 需论证"example 未覆盖 tests[] 执行 + 无生产 pull-lab 执行器"，或承诺长期换 tuxrun。
7. peer 仓库(xjysiiau/Acidmoon)用 SSH/log-grep 绕开 PTY，均非 pull-lab 形态，**不要**拿它们行数当"别人 worker 就这么点"的证据。
8. 证据可靠度：本地与上游 main 四文件 SAME(diff 实测)、tuxrun/tuxlava/lava 均下载到 /tmp 逐文件计数；kernelci-core PR#3008 只抓到标题/作者/日期(正文未能从 HTML 抽取)，QEMU ssnpm≥9.1 仅用户实测+qemu-devel 补丁线索，均标未验证。
