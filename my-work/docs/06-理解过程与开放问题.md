## 1. 疑惑轨迹(按讨论顺序,记录每个问题的答案与现在的回看)

### 1.1 "我加几十行配置 PR 上去,能提交吗?上游凭什么合?我没有服务器"
- ✅ 核实结果:**LAVA 与 pull_labs 的差别在连接方向**。LAVA 是 push(官方主动 POST 任务到你的服务器,必须公网可达);pull_labs 是 pull(官方只把 node 置 available + 挂任务书,lab 主动刷走,**零入站流量**)。
- ✅ pull_labs 的惰性是官方设计:上游现存的 pull-labs-demo/aws-ec2/pengutronix 都是"配置在、lab 各自运营"的形态。
- 💭 判断:**"没有服务器 → PR 不该合"是误解**;PR1 合入不依赖我们上线 lab。合入判据 = 配置规范 + 档案完整,不取决于谁在跑。
- ❓ 待验证:上游 review 会不会要求"先有 lab 在线的证据"。我们的对策:PR 描述里带真跑日志链接。

### 1.2 "LAB 很难写;改引擎难不难合?"
- ✅ 核实:"引擎缺口"就是 00 §7 的三处,其中 1+2(补 `get_meta`、去 `lava.Callback` 硬编码)是**几十行、纯加法、填官方自己留的坑**;3(prepared state)要动 API 状态模型,最重且非必需。
- 💭 判断:1+2 属于"补引擎缺口而非重复造轮子",合并风险低(不改变任何现有 lava 路径行为);比单独交 worker 分量大得多。
- ❓ 开放:上游会不会要求把 #3 一并做掉才肯合 1+2。

### 1.3 "为什么执行器不用 PR?那到底 PR 什么?"
- ✅ 核实:worker 只在我们的机器上运行,上游无法运行/测试/维护;上游 lab 侧只有 example(演示)+ 协议文档,真实 lab(pengutronix/aws-ec2)的执行器都不在上游仓库。
- 💭 结论(此为定论,已在 00 落过):PR 三件套 = PR2(tuxlava 4 行登记)→ PR1(64 行配置)→ PR3(服务端回收 1+2);worker 公开到自家 repo、贴 tracking issue,但不 PR。

### 1.4 "他怎么知道我做的对不对?他怎么认我的上传?"
- ✅ 核实:回调端点逐 token 比对(401 拒收);结果只能挂到官方生成的 node id 上;任务书(内核/rootfs/命令)全部公开 URL。
- 💭 结论:**信任模型 = 可证伪 + 追责,而非官方亲眼验证**。四层:token 锁身份、node id 锁单据、公开任务书 + 官方 tuxrun 让任何人可重跑打脸、声誉追责。
- ❓ 延伸讨论过"指纹/TEE 能否防死造假":结论是指纹只能防调包、防不了撒谎,且测试是"一次测量"不可哈希复现;分布式 CI 通行的答案是"让造假期望收益为负"。这属于行业认知,不再投入。

### 1.5 "脚本要不要公开?能不能随意写?"
- 💭 结论:**不提交 ≠ 不公开**。公开到自家 repo = 接受查账(成本为零);不 PR = 上游不替你维护。
- ✅ "复现不靠脚本":真正生产结果的是公开任务书 + 官方 tuxrun,worker 只是快递员。脚本写烂,砸的是自己 lab 的招牌,不是上游的流程。

### 1.6 "工作流是一定的吗?YAML 到底决定了什么?"
- ✅ 核实:YAML → 官方代码是**硬映射**(runtime 工厂按 lab_type 拼模块名、job 名选模板、event 名触发 scheduler)。官方这半截,写 YAML 即定死。
- ✅ 但 `type: pull_labs` 的语义 = "官方代码执行到 node 置 available 为止";lava/docker/shell/k8s 都是官方跑全程,**唯独 pull_labs 后半截官方留白**。
- 💭 结论:工作流分三段——我们的 YAML(声明)→ 官方代码(解释器,不碰)→ 我们的 worker(填留白)。这就是"既要交 YAML 又要留 worker"的原因。

### 1.7 "任务肯定得有人接,谁接?怎么接?"
- ✅ 核实:worker 无"认领"动作(不改 node 状态、不握手),跑起来刷到单就执行;有 platform/runtime 过滤 + flock 防重。
- 💭 结论:**我们就是接单员**。SOW 里"未来的 RISC-V lab"= 我们 + 我们的机器。token 是我们的工牌;开机运行 = 接单;关机 = 单子攒着,没人催。将来不干了,官方换发 token,配置一行不改。

### 1.8 "传个话为什么要 500 行?"
- ✅ 拆账(按函数边界数):轮询/取单/送回 ~40 行;翻译层(烤 ext4/解包/cpu 参数/KSELFTEST overlay)~110 行;TAP 判读 + 打包 ~50 行;工程胶(状态文件/flock/去重/重试/游标)~100 行;骨架 ~60 行。
- ✅ 对照:官方 example_pull_lab.py 361 行(还不用 POST、不重试);我们纯代码 361 行,多出的 78 行 = 演示→生产的距离(00 §5 已有账)。
- 💭 结论:**没虚胖**;若只写 60 行快递员,会撞上六种真实死法(riscv 设备不认 cpio、tuxrun 假 pass、断网丢单、双开抢单、停电漏单、刷错别人的单)。

### 1.9 "110 行债和 50 行解析具体是什么?"
- ✅ 110 行翻译层的五个坑(全部有真实来源):(1) qemu-riscv64 不认 cpio → 烤 ext4;(2) 容器内下载大 rootfs 截断 → 宿主预下载;(3) tar 解包安全过滤;(4) kselftest tarball 走 `--parameters KSELFTEST=` + tuxrun 不认识 kselftest-riscv 类(PR2 修);(5) KVM 要 `h=true`。
- ✅ 50 行:`tap_summary` 纠 tuxrun 的假 pass(not ok 但退出码 0,上一会话真抓到的 bug);`result_body`/`error_body` 按协议打包。
- 💭 **本次讨论的一次自我修正**:讨论中途曾把"50 行解析"说成"PR3 后还给上游"——回看协议后修正为:**TAP 判读删不掉,是 lab 本职**(协议要求 lab 自己把 tuxrun 输出算成 summary/tests);PR3 真正改变的是让这 50 行的产出**从"对空发射"变成"有人签收"**。记下这个修正,防止下个会话沿用错误说法。

### 1.10 "为什么不能直接修?"
- 💭 结论:**能修的你已经在修**(PR2 就是直接修)。策略 = 垫片顶住现在 + PR 并行修 + 上游发版后删垫片。三类:能修已修(PR2、可提的 tuxrun 假 pass 修复);feature 类按月等(ext4 支持、自动 h=true);不归官方管(下载截断、安全解包)。**直接修 = 上游 PR = 删本地代码**,是一条路的两个阶段。
