## 2. 架构:一个 job 的一生 + QEMU 参数链

```
① 配置声明    config/{platforms,jobs-pull-labs,scheduler-pull-labs,pipeline-pull-labs}.yaml
② 渲染任务书  scheduler 用 config/runtime/*-pull-labs.jinja2 渲染 job 定义 JSON
③ 取单+执行   my-work/tools/lab/riscv_pull_worker.py(docker 跑 linaro/tuxrun-dispatcher;tuxrun+tuxlava)
④ 判读+回传   worker 的 lava_body()/post_result() → LAVA 兼容 body
⑤ 入库        lava_callback.py(kernelci-pipeline/src:525 = kernelci.runtime.lava.Callback)
```

QEMU 参数谁决定(逐层):
- `config/platforms.yaml:577 qemu-riscv64` 声明 `arch: riscv / cpu: rv64,v=true / machine: virt / memory: 4G`(**当前 worker 不读 machine/memory**);
- worker `build_command()`(riscv_pull_worker.py:311-385)决定:`--device qemu-riscv64 --boot-args rw --rootfs(file://ext4 或 URL) --tests kselftest-* --parameters cpu=... KSELFTEST=... TST_CASENAME=...`;
- tuxlava `QemuRiscV64` 设备类(~/.local/lib/python3.10/site-packages/tuxlava/devices/qemu.py:514)拼 qemu argv:machine=virt、cpu=rv64、`-smp 2`、`-drive ...if=virtio`、console=ttyS0;
- cpu 串:kvm job 自动补 `,h=true`(worker `cpu_for()`,303-310)。

任务书 JSON 长什么样:草案 §3 的 shape 基本对(artifacts/tests[type,timeout_s]/callback{url,token_name})——**没有"用哪个容器"字段**;执行器归 lab 私有(三种 example:tuxrun / lava / pytest,上游 tools/ 均有)。

## 4. 高频问答(压缩版,依据即 §3 行号/文件)

### 4.1 worker 为什么 889 行?(2026-09-09 已删 5 项过度防御,原 1008)
889 = docstring ~150 + 常量/正则 ~90 + 判分 ~120 + LAVA 打包 ~105 + 状态机 ~250 + 翻译执行 ~130 + argparse ~70 + 下载/烤盘 ~75。删不掉的三大头:**TAP 判分**(防假绿)、**lava_body**(上游只认 LAVA 格式)、**poll_loop/handle_event**(游标重叠+seen+flock+重试)。
2026-09-09 删掉的 5 项过度防御:mask_url、sha256 校验、url_allowed(下载白名单)、tar 解包 containment、url_allowed(回调白名单)——依据"上游任务书可信",-119 行。保留 `allow_redirects=False`(防 token 被重定向带走,不是防上游)。
真正的"翻译任务书→跑 tuxrun"业务只有 build_command+run_command+run_job ~130 行;删不掉的都在这三块,别再往下砍。

### 4.2 worker 为什么不提交?
上游把 lab 当黑盒:只要求"接得到单 + 按 LAVA body 回传真结果";执行器归 lab。真 lab 全没交执行器;上游 tools/ 只有 example 脚本(已跟踪,git ls-files 可见)。提交 worker = 多一轮 review 无收益。**PR1(配置)才是唯一必交。**

### 4.3 怎么防伪 / 防跑错 / 假绿?
- 防伪(token):`Authorization: Token <env>` 值只存环境变量;`allow_redirects=False` 防 token 被重定向带走(2026-09-09 已删 `--allowed-hosts` 白名单,上游任务书可信)。
- 防跑错:判读规则对生产同款解析器验证(verify-lava-body,真 PASS/FAIL 日志喂 `kernelci.runtime.lava.Callback`,全绿);日志随节点上传可复核。
- 防假绿:证据不足一律不给 pass——无 boot case / TAP 空 → incomplete + `error_type: Infrastructure|Job`(worker:514-530);`not ok` 变体全在 verify-worker-guards(全绿)。
- 上游无自动内容校验;信任模型=准入(#1313/#1357/#1477/#1509 均为受信任机构,零 review)+ 公开数据 + 节点只能挂真实已派单。

### 4.4 两个 SKIP 是什么?(日志原文 trixie-kvm2.log)
`sbi_pmu_test` → `# SKIP - SBI PMU not available`(平台无 SBI PMU 采样支持);`irqfd_test` → `# SKIP - Requirement not met: kvm_arch_has_default_irqchip()`(riscv64 KVM 无默认 irqchip)。**guest 测试自己声明并带原因,与配置对错无关**,QEMU 与真机结论一致。

### 4.5 token 机制(极简)
名字=pipeline 配置里(public);值=部署方 kernelci.toml `[runtime.pull-labs-riscv] runtime_token=...`(secret,占位符原文 `REPLACE_WITH_CALLBACK_TOKEN_VALUE`,connecting-pull-lab.md:77-94),带外交给 lab → `export PULL_LABS_CALLBACK_TOKEN`。scheduler 需 `--runtimes pull-labs-riscv`。**无"PR 后自动发 token"机制。**

### 4.6 patch 怎么生效?
一次性 `patch -p1` 改**已安装包**文件(tuxlava 0.24.0,~/.local site-packages;已 grep 到 KSelftestRiscv)。运行时无人读 .patch;重装 tuxrun 需重打;不提交也生效(改的是本机包)。正确归宿=推 kernelci/tuxrun 上游。**PR1 描述需声明此补丁存在。**

### 4.7 lab 模型:要不要 review / 纯信任?
配置 PR 有 review(简单所以零评论);执行器不 review。token 只证"有资格",不证"测得对"。上游防的是陌生人冒充,不是注册 lab 造假;后者靠公开+声誉+真实节点锚定。

### 4.8 PoC 是什么?
Proof of Concept=最小实证:真实节点(6a9fb8bfdb925f2f584f0771,state=done/result=pass,构件齐全)、9/9 与 7ok/2skip 日志、validate_yaml 输出。nuclearcat #1313 被问"有结果了吗?"即用 PoC node_id 过关(07:68-73)。**提交 ≠ 跑**:配置合入不触发任何运行;跑=注册 runtime+token+lab 常驻 worker。PR 描述要把"现在谁跑/以后谁跑(hand-off)"写清楚。

### 4.9 节点/证据存哪?
- 结果节点:mongo(docker 容器 kernelci-api-db,卷 mongodata)——**不可 git 备份**;
- 构件/日志:`kernelci-api/docker/storage/data/<job>-<node_id>/`(如 baseline-riscv64-qemu-worker-6a9fb8bf…);
- lab 现场副本:`my-work/evidence/worker-out/`(job-*/tuxrun.log)、`callback-received.json`。
⚠️ `docker compose down -v` 会清 mongo;要带走的证据=storage/data 节点目录 + worker-out + 复跑命令。

### 4.10 config drift 与 regression 是什么(两个 Phase 2 feature,不进 PR1)

### 4.13 LAVA 回传契约:5 字段,谁定的、缺了会怎样
契约定义方 = `kernelci-core/kernelci/runtime/lava.py` 的 `Callback` 类(唯一解析器);消费方 = `lava_callback.py:332-399`。body 是"假 LAVA 服务器"格式,pipeline 只认它(PULL_LABS 协议体未接线,发出去静默丢)。

|---|---|---|---|

## 5. pull-only 协议草案(v0.2)vs 现实——对照要点

草案(nuclearcat Google Doc,Draft v0.2,含 §18 To-Decide):Bearer 双 token、/accept 领单、/status 进度、/results + Idempotency-Key、自造 JSON schema、状态机 ready→accepted→running、事件严格有序。

**结论:草案是路线图不是规格;worker 以"lava_callback + pull_labs.py"的真实接线为准。引用草案时别说"严格有序",会被 overlap 窗口打脸。**

## 10. 经验总结(2026-09-09 三轮答疑后新增)

1. **收口优先于打磨**:链条长(配置→渲染→取单→执行→判读→回传→入库),一个人不可能每环都精通;可操作的标准 = "跑通 + 验证 + 能回传",不是"每行都懂"。
2. **格式对不对有机器查,不必每步都做对**:verify-lava-body.py 喂生产 Callback + 上游 4xx 报错,双重兜底;手工试错是浪费。
3. **历史错误结果不用删、不用坦白**:结果按 kernel 版本滚动,staging 是测试环境,旧版本自然过时;生产 demo 本身 96% node_timeout、fail=0,没人追责。开源 review 看代码不看"AI 还是人写"。
4. **删防御是次要矛盾**:大头是判分(防假绿)+LAVA 打包(上游只认这格式)+状态机(防重跑),这三块删不掉;删掉的 5 项防御证明"上游任务书可信"成立。
5. **"不完全懂"是常态,不是缺陷**:交接文档(00-09)+verify 脚本承载记忆;剩余不懂交给上游 reviewer 在 PR 里指出,比自己本地猜一百遍准。
6. **下一步只有一件事:发 PR1**。配置已就绪、token 机制已明、worker 已验证、生产已对比;继续本地打磨边际收益≈0。
