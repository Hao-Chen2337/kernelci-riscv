# kcilib/

The library the RISC-V pull lab runs on: the execution kernel one job goes through, and the vocabulary that names it (a build, a job, an outcome, a source, a sink). 34 modules, ~7.9k lines. Nothing here runs a kernel test without it, and all five entry points — `scripts/riscv_pull_worker.py`, `scripts/fetch-and-run-latest.py`, `scripts/local-jobs.py`, `scripts/dashboard.py`, `scripts/results.py` (1965 lines between them) — import `kcilib` (four of them nothing else of this repository; `dashboard.py` also imports the two offline tools under `scripts/tools/`).

## The three lines, one execution kernel

The kernel is one function, `kcilib.run.jobrun.run_node()`: a job definition in, a ledger row and a callback body out. A job the worker claimed and a job this repository invented are the same input to it — it cannot tell, and must not. The three lines differ only in where that definition comes from.

| # | The line | Entry point | What it stands on |
|---|---|---|---|
| ① | resident worker: claim a job from the events API, run it, post the result back | `scripts/riscv_pull_worker.py` | `core/{cli,config,state}`, `run/{poll,jobrun,judge,runner,callback,artifacts,bake}`, `sink` |
| ② | one-shot: the newest production build, fetched and run once | `scripts/fetch-and-run-latest.py` | `core/{config,layout,policy}`, `model/` (which stands on `table/build.py`), `run/{artifacts,bake,delivery,judge}` |
| ③ | local job table: index − ledger, run offline | `scripts/local-jobs.py`, plus `dashboard.py` and `results.py` | `api`, `table/{build,buildindex}`, `model/`, `core/ledger`, `sink` |

## Importing it

Put `scripts/` on `sys.path` (each entry point inserts it from its own directory, so a caller only needs the checkout), then name the module:

    from kcilib import repo_root
    from kcilib import api, sink
    from kcilib.core import config, layout, policy
    from kcilib.core.ledger import test_of
    from kcilib.model import Build, Builds, Job, Jobs, Outcome, get_source
    from kcilib.run import judge
    from kcilib.run.jobrun import run_node

`kcilib.model` is the top of the stack and **nothing below it may import it back**. That direction is enforced, not described: `scripts/tools/guards/references.py` parses every module with `ast` and fails on `api.py` importing anything of this package, `sink.py` importing `kcilib.model`, `core/` importing `run/`|`table/`|`model/`, `run/` importing `table/`|`model/`, or `table/` importing `model/` — `model/` -> `table/` is the layer's shape, not a violation. The same guard bans a `ROOT`-ish module constant built by counting `os.path.dirname()` levels (the root is walked up to by `repo_root()`). Flat spellings are gone with the sub-packages: `from kcilib import judge` does not import, and every `python3 -m kcilib.X` in shell must resolve to a real module.

## Module index

## Owner table: who decides what

Find the owner before changing a behaviour: an edit anywhere else is a second spelling of the same decision, and the guard suite reads these names. (docs/ARCHITECTURE.md, section 5, calls these "the ten owners"; its pairs add up to eleven entries, and this table lists all eleven.)

| The decision | Its owner |
|---|---|
| where a result goes | `kcilib/sink.py` -> `sinks_for()` |
| running one job | `kcilib/run/jobrun.py` -> `run_node()` |
| the verdict | `kcilib/run/judge.py` |
| the command line | `kcilib/run/runner.py` |
| the ledger's layout and key set | `kcilib/core/ledger.py` |
| what a job is called | `kcilib/core/ledger.py` -> `test_of()` |
| where bytes live under `work/` | `kcilib/core/layout.py` |
| every how-many / how-big / how-long number | `kcilib/core/policy.py` |
| CLI flag -> config field | `kcilib/core/config.py` -> `from_args()` |
| the repository root | `kcilib/__init__.py` -> `repo_root()` |
| which jobs a build has | `kcilib/model/jobs.py` -> `jobs_for()` |

## Test seams

The guard suite and the one-shot line drive real code with the real surrounding machinery, by **rebinding a module-level name on the module that owns the call**. That is the only reason these names may not move into a closure, a nested import or a local alias: a name bound inside a function is not resolved on the module at call time, so `jobrun.run_command = <stub>` would have no effect and the test would silently exercise the real `tuxrun`.

| Rebindable name | What it owns |
|---|---|
| `run/bake.py` -> `stamp` | the `[HH:MM:SS]` progress printer (`jobrun` and `poll` re-export it as their own attribute) |
| `run/bake.py` -> `download` | the bake path's one artifact transfer |
| `run/poll.py` -> `requests`, `run/callback.py` -> `requests`, `run/artifacts.py` -> `requests` | the HTTP call itself: stub the module that owns it, never a caller's |
| `run/jobrun.py` -> `run_command` | running `tuxrun` and capturing its console |
| `run/jobrun.py` -> `run_tuxrun` | the executor `run_command` delegates to (the one-shot line swaps in its own console capture around one `run_node()` call) |
| `run/jobrun.py` -> `baked_rootfs_image` | tarball -> bootable ext4, cache included (a boot job must never bake) |
| `run/jobrun.py` -> `stamp` | the progress lines `run_node` labels its work with (silenced for the one-shot line) |
| `run/poll.py` -> `fetch_nodes` | the events API call, and nothing else |
| `run/poll.py` -> `retrieve_job_definition` | fetching one node's job definition |
| `run/poll.py` -> `handle_event` | one event's whole handling, with the run function injected |

`run_node` itself takes the injection route instead: `poll_loop(poll_config, run_node, run_config)` receives the run function, so a test passes a stub rather than patching an import — and `Job.run()` assembles a `RunConfig` plus a definition and hands them over, so nothing below has to be patched to exercise the model layer.

## Where to read more

* `docs/ARCHITECTURE.md` — the maintainer's document: layer diagram, ownership table, data flow, the six invariants, the seams, and a "how do I change X" section naming the guard that pins each change.
* `docs/RUNBOOK.md` — the public operator guide: the commands, the local stack, the failure modes. The one file under `docs/` tracked in git.
